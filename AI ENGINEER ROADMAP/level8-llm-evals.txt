Level 8 · LLM Evals

Scope: prove that an LLM system actually works, understand where it fails, and prevent quality regressions. Evaluate models, RAG pipelines, and agents using reproducible test sets instead of demos and intuition.

M8.1 · Eval-driven development — (sessions: 1)

Understand why traditional unit tests are not enough for probabilistic LLM systems.
Treat evals as a continuous engineering loop: define behavior → measure → inspect failures → improve → measure again.
Distinguish offline evals from online/production evaluation.
Understand the different evaluation targets: model → component → workflow → complete application.
Define success criteria before changing prompts, models, retrieval logic, or architecture.
Outcome: Make system changes based on measured quality rather than intuition.

M8.2 · Golden datasets & test-case design — (sessions: 2)

Build representative test cases containing input, expected behavior, reference answer/context where appropriate, and metadata.
Cover normal cases, edge cases, known failures, ambiguous inputs, and adversarial cases.
Create test cases manually as well as from production failures, user feedback, and sampled real-world interactions.
Organize examples by task type, difficulty, language, query category, or other useful dimensions.
Version datasets alongside prompts, models, and application changes.
Avoid repeatedly optimizing against a tiny fixed dataset until it stops representing real usage.
Outcome: Build and maintain a golden dataset that represents the real behavior your application needs to handle.

M8.3 · Metrics & evaluation methods — (sessions: 2)

Understand reference-based vs reference-free evaluation.
Use deterministic metrics where possible: exact match, accuracy, precision, recall, F1, execution success, schema validity, and task-specific programmatic checks.
Use semantic similarity when correct answers can have different wording.
Understand BLEU/ROUGE and why lexical overlap alone is often insufficient for modern LLM applications.
Distinguish objectively measurable behaviors from subjective qualities such as helpfulness, completeness, style, and coherence.
Choose metrics based on the task instead of searching for one universal LLM-quality score.
Combine several complementary metrics when application quality has multiple dimensions.
Outcome: Choose the simplest reliable evaluation method for the behavior being measured.

M8.4 · LLM-as-a-Judge — (sessions: 3)

Use LLMs to evaluate qualities that are difficult to measure using deterministic code.
Design clear criteria, rubrics, scoring scales, and judge prompts.
Implement binary pass/fail, pointwise scoring, and pairwise comparison.
Understand when pairwise comparison is more reliable than assigning absolute scores.
Use reference answers or source context when the evaluation criterion requires them.
Calibrate judge outputs against human-labelled examples.
Understand common judge failure modes such as position bias, verbosity bias, self-preference, inconsistent scoring, and weak rubric interpretation.
Improve judge reliability using explicit rubrics, structured outputs, randomized ordering, and repeated evaluation where appropriate.
Keep the evaluated system and the judge logically separate; avoid blindly trusting a model to evaluate itself.
Outcome: Build an LLM judge whose behavior has been validated rather than assuming judge scores are automatically trustworthy.

M8.5 · RAG evaluations — (sessions: 2)

Evaluate RAG at the retriever, generator, and end-to-end pipeline levels.
Measure retrieval quality using metrics such as Recall@k, Precision@k, MRR, and contextual relevance where appropriate.
Evaluate generated answers using faithfulness/groundedness, answer relevance, correctness, and citation support.
Understand contextual precision and contextual recall and how they differ from ordinary document-level retrieval metrics.
Diagnose whether a poor final answer came from retrieval failure → poor context → generator failure.
Evaluate the generator independently when useful by supplying known-good context and measuring whether it answers faithfully and relevantly.
Compare changes such as chunking, embedding model, k, reranking, query transformation, and prompting using the same test set.
Use frameworks such as DeepEval and RAGAS while understanding what their metrics are actually computing.
Outcome: Evaluate individual RAG components separately and determine which part of the pipeline is responsible for poor quality.

M8.6 · Agent evaluations — (sessions: 2)

Understand why evaluating only the final response is insufficient for agentic systems.
Evaluate task completion, trajectory quality, tool selection, tool arguments, tool-result usage, and stopping behavior.
Check whether the agent chose the correct tools and used them in an appropriate order.
Detect unnecessary tool calls, repeated actions, loops, incorrect handoffs, and failed recovery attempts.
Evaluate whether the agent successfully adapts when a tool fails, information is missing, or intermediate results are unexpected.
Measure both outcome quality and execution efficiency.
Track operational dimensions such as latency, token usage, tool-call count, number of steps, and total cost.
Outcome: Determine not just whether an agent succeeded, but whether it followed a reliable and efficient trajectory.

M8.7 · Observability & tracing — (sessions: 2)

Trace complete LLM executions containing prompts, model calls, retrieval, tools, retries, agent steps, and final responses.
Capture the actual inputs and outputs at every important step in a multi-stage application.
Track operational metrics such as latency, TTFT, token usage, cost, errors, retries, and tool-call frequency.
Use observability platforms such as Langfuse or Phoenix to inspect complex runs.
Connect evaluation failures back to the exact traces that produced them.
Debug failures by inspecting what context the model received, what was retrieved, which tools were called, and what those tools returned.
Identify which step is responsible for unexpected cost or latency.
Understand the distinction between evals for measuring quality and tracing for understanding why a particular run behaved the way it did.
Outcome: Reconstruct and debug the execution of a complex LLM system rather than treating it as a black box.

M8.8 · Regression testing & evals in CI — (sessions: 1)

Convert important evaluation examples into a permanent regression suite.
Automatically run evals when prompts, models, retrieval logic, tools, or application code change.
Compare candidate versions against an existing baseline.
Define acceptable quality thresholds and prevent changes from shipping when important metrics regress.
Track quality alongside latency and cost so an accuracy improvement does not silently make the application prohibitively slow or expensive.
Separate lightweight CI evals from larger and more expensive evaluation suites.
Outcome: Treat LLM quality as a release criterion rather than something manually checked after deployment.

M8.9 · Production evals & feedback loops — (sessions: 1)

Sample real production interactions and evaluate them continuously.
Use explicit user feedback, implicit behavior, support issues, and observed failures to discover gaps in the offline test set.
Monitor quality across prompt versions, models, user segments, and application changes.
Add important production failures back into the golden dataset.
Understand the continuous loop: production failure → new eval case → fix → regression test → redeploy.
Combine offline evals with production signals rather than assuming either is sufficient on its own.
Outcome: Build an evaluation system that becomes more representative as the application encounters real-world usage.
M8.10 · Capstone: CI-Gated Evaluation Suite — (sessions: 1)
Choose an existing RAG or agent application from earlier levels.
Create a versioned golden dataset containing representative examples, edge cases, and known failures.
Implement a combination of programmatic metrics, semantic metrics, and LLM-as-a-judge where appropriate.
Add component-level evaluation for retrieval/tool use in addition to evaluating the final output.
Track quality, latency, token usage, and cost.
Add tracing so failed eval cases can be inspected at the execution level.
Integrate the suite into CI and define a threshold where a meaningful quality regression causes the PR/build to fail.
Feed future production failures back into the suite.
Final result: an application where changes cannot ship merely because a few manual demos still look good.
Level 8 completion outcome

By the end of this level, you should be able to:

Design representative golden datasets and maintain them over time.
Choose between deterministic, semantic, reference-based, and reference-free evaluation methods.
Build and calibrate LLM-as-a-judge evaluators.
Evaluate RAG retrieval, generation, and the complete pipeline separately.
Evaluate agent outcomes, trajectories, tool usage, and recovery behavior.
Trace complex LLM applications and diagnose failures from their execution history.
Measure quality alongside latency, token usage, and cost.
Build permanent regression suites.
Run quality checks automatically as part of CI.
Use production feedback to continuously improve evaluation coverage.
Practice eval-driven development as the default way to improve an AI system.
