Level 10 · LLMOps: From Development to Production

Goal: Take the RAG application and the agent you have already built into production — versioned, evaluated on every change, guarded, containerized, deployed on AWS, and monitored — and keep them improving once real users arrive.
Prerequisites: Level 0 (containers), Level 4 (RAG), Level 5 (agents), Level 7 (evals), Level 8 (security) · Depth: Hands-on; an AWS account is required · Suggested duration: 23 sessions.

M10.1 · What LLMOps adds — (sessions: 1)

Understand LLMOps as the practice of shipping, operating, and improving LLM applications, and where it overlaps with and departs from classic MLOps.
Distinguish application LLMOps, which runs products on top of existing models, from model LLMOps, which trains and hosts the models themselves, and recognize that most teams practise the first.
Understand what makes LLM systems harder to operate: non-deterministic outputs, prompts that change behavior without a code change, provider-side model updates, and a cost attached to every request.
Define what a release actually is for an LLM application: code, prompts, model version, retrieval configuration, index contents, and tool definitions, all of which must be versioned together.
Understand how operating a RAG application differs from operating an agent, from stale indexes and retrieval drift on one side to runaway loops and tool failures on the other.
Map the lifecycle this level follows: track → evaluate → guard → serve → ship → deploy → monitor → improve.
Try: List every change that could alter your RAG application's answers tomorrow without anyone editing its code, and note which of them you could currently detect.
Mental model: Code + prompts + model + data + tools = one release, and every part of it can change behavior
Outcome: Explain what has to be versioned, tested, and watched for an LLM application to be safe to change.

M10.2 · Preparing your apps for production — (sessions: 1)

Take the RAG application from Level 4 and the agent from Level 5 as the two systems this level operates, rather than building new ones.
Separate configuration from code, so the model, prompts, retrieval parameters, and tool set can change without a rewrite.
Pin model versions and dependency versions, so a rebuild next month produces the same system as today.
Make each request traceable from the start by attaching a request ID, the prompt version, and the model version to everything it touches.
Carry the evaluation dataset from Level 7 forward as the fixed yardstick every later change will be measured against.
Try: Change the chunk size and the model of your RAG application through configuration alone, and confirm that no code had to change.
Outcome: Have two applications structured so that every behavior-changing setting is explicit, versioned, and recorded.

M10.3 · Experiment tracking & prompt versioning — (sessions: 2)

Session 1 · Tracking experiments
Record each experiment in MLflow with its parameters, such as chunk size, top-k, model, temperature, and tool set.
Log evaluation scores as metrics and keep prompts, configurations, and sample outputs as artifacts of the run.
Compare runs side by side to see which change actually moved quality, latency, or cost.
Record a baseline run for both applications before changing anything.
Session 2 · Versioning prompts
Store prompts in a prompt registry such as Langfuse, so they are versioned, reviewed, and deployed independently of code.
Label prompt versions for staging and production, and promote a version by moving the label rather than editing text in place.
Fetch prompts at runtime with caching and a pinned fallback, so a registry outage does not take the application down.
Roll back a bad prompt by moving the production label back to the previous version.
Link every trace to the prompt version that produced it, so a regression can be traced to the change that caused it.
Try: Ship a second version of a prompt behind the staging label, compare it with production on your evaluation set, then promote or reject it.
Outcome: Keep a reproducible history of every prompt and configuration, and change either one without a code deployment.

M10.4 · Evaluation as a release gate — (sessions: 2)

Session 1 · Wiring the suite into the build
Turn the Level 7 evaluation suite into automated tests that run with DeepEval inside an ordinary test runner.
Score the RAG application on faithfulness, answer relevance, and contextual precision, and the agent on tool selection, task completion, and step efficiency.
Set a threshold per metric against the recorded baseline, and fail the build when a change falls below it.
Extend coverage with synthetic test cases generated by DeepEval, reviewed by a person before they join the suite.
Session 2 · Making the gate trustworthy
Handle non-determinism by repeating runs, using tolerance bands, and fixing sampling settings where the task allows it.
Budget evaluation cost and time by running a fast subset on every change and the full suite before release.
Treat a prompt change, a model change, and a retrieval change exactly like a code change, so all of them pass through the same gate.
Record every gated run in MLflow, so the history of a metric shows which release moved it.
Try: Deliberately weaken a prompt, push it, and confirm that the gate blocks it with a clear report of which metric failed.
Outcome: Make it impossible for a change that lowers measured quality to reach production unnoticed.

M10.5 · Runtime guardrails — (sessions: 2)

Session 1 · Validating inputs and outputs
Turn the threat model from Level 8 into runtime checks that run on every request, in front of and behind the model.
Enforce structured outputs with Guardrails AI, validating against a schema and re-asking the model when validation fails.
Define topical and conversational rails with NeMo Guardrails, and understand when that framework suits better than a validator.
Check inputs for prompt injection attempts and personal data, and outputs for ungrounded claims, off-topic answers, and leaked secrets.
Session 2 · Limiting agents and measuring the guards
Validate tool arguments before execution, and cap agent steps, retries, and spend per request so a loop cannot run unbounded.
Measure what each guardrail costs in latency and how often it blocks a legitimate request.
Log every block and every re-ask, so guardrail behavior can be reviewed and tuned rather than trusted blindly.
Try: Send ten injection attempts and ten legitimate edge cases through your guarded application, then count what was blocked wrongly in each direction.
Outcome: Run both applications behind input, output, and agent guardrails whose cost and false-positive rate you have measured.

M10.6 · Application serving & containerization — (sessions: 3)

Session 1 · A production backend
Move application logic out of notebooks and scripts into a FastAPI backend with validated requests and typed responses.
Stream responses token by token with server-sent events, so users see the answer forming instead of waiting for all of it.
Set timeouts and handle client disconnects, so an abandoned request stops consuming model tokens.
Expose health and readiness endpoints that report whether the model provider and vector database are reachable.
Session 2 · A thin frontend
Build a Streamlit frontend that only renders the interface and calls the backend, holding no application logic of its own.
Render the streamed response and surface errors, timeouts, and guardrail blocks to the user in plain language.
Session 3 · Containers
Package the backend and frontend as Docker images with small, reproducible builds.
Run the backend, frontend, and the vector database your RAG application already uses together with Docker Compose.
Supply secrets and API keys through the environment at runtime, never baked into an image.
Try: Start the whole stack with one Docker Compose command on a clean machine, and confirm that streaming still works through every layer.
Outcome: Serve both applications as a streaming, containerized stack that runs the same way on any machine.

M10.7 · CI/CD with GitHub Actions — (sessions: 2)

Build a GitHub Actions pipeline that runs unit tests, then the evaluation gate, then builds an image, in that order.
Tag every image with the commit it was built from, and push only images that passed the gate to a registry such as Docker Hub.
Store provider keys and registry credentials as pipeline secrets, and keep them out of logs and pull-request builds from forks.
Require a manual approval before a release reaches production, while allowing staging to deploy automatically.
Keep the previous image deployable, so a rollback is a redeploy of a known tag rather than a rebuild.
Try: Open a pull request that changes only a prompt, and follow it through the gate, the build, and the push.
Mental model: Push → unit tests → eval gate → build & tag → registry → staging → approve → production
Outcome: Automate the path from a commit to a tested, tagged, deployable image, with quality enforced before anything ships.

M10.8 · Deployment on AWS — (sessions: 3)

Session 1 · Servers, identity and secrets
Provision EC2 instances for the application, install Docker, and attach an IAM role instead of storing access keys on the machine.
Store provider API keys in AWS Secrets Manager and load them when the container starts.
Session 2 · Automated releases
Use AWS CodeDeploy to pull a tagged image and replace running containers, with health checks deciding whether the release continues.
Choose between in-place and blue/green releases, and roll back automatically when the new version fails its health checks.
Session 3 · Traffic and scale
Put an Application Load Balancer in front of the instances, and raise its idle timeout so long streamed responses are not cut off.
Add an Auto Scaling group that adds instances when busy and removes them when quiet.
Scale on request concurrency rather than CPU, since an LLM application spends most of its time waiting on the model provider.
Recognize that provider rate limits usually cap throughput before your servers do, and size scaling with those limits in view.
Try: Load-test the deployed application until it scales out, then check whether the bottleneck was your instances or the provider's rate limit.
Outcome: Run both applications on AWS with automated releases, health-checked rollbacks, load balancing, and scaling.

M10.9 · Monitoring & observability — (sessions: 3)

Session 1 · Infrastructure and application metrics
Run Prometheus to collect metrics from every instance, using Node Exporter for CPU, memory, disk, and network.
Export application metrics from the backend: requests, latency percentiles, errors, model calls, tokens, and guardrail blocks.
Session 2 · Dashboards and alerts
Build Grafana dashboards that show server health, traffic, latency, error rate, and token spend side by side.
Alert on the signals that need a human, such as error-rate spikes, latency beyond budget, failed scaling, and spend above a daily limit.
Session 3 · Tracing and online evaluation
Trace every request in Langfuse through retrieval, model calls, and tool calls, with latency and cost recorded at each step.
Run online evaluations on a sample of live traffic, and collect user feedback alongside them.
Turn production failures found in traces and feedback into new cases for the Level 7 evaluation suite.
Try: Find the most expensive request of the past day in your traces, and explain where its tokens went.
Outcome: See server health, application behavior, cost, and answer quality for the live system, and feed what you find back into evaluation.

M10.10 · Incidents, rollbacks & change management — (sessions: 1)

Recognize the incidents specific to LLM applications: a provider outage, a silent model update, a prompt regression, a stale index, a runaway agent, and a cost spike.
Respond with the lever that matches the cause: a model fallback, a prompt rollback, an image rollback, an index rebuild, or a spend cap.
Write a short runbook per incident type, naming the signal that detects it, the first action to take, and the person who decides.
Re-run the evaluation suite whenever the provider announces a model change, before the change reaches your users.
Run a blameless review after each incident, and add the case that caused it to the evaluation suite.
Try: Simulate a provider outage in staging and time how long the application takes to fall back and recover.
Outcome: Detect, contain, and recover from LLM-specific incidents with a practised response rather than improvisation.

M10.11 · Capstone: LLMOps Project — (sessions: 3)

Take the agent from Level 5 or the RAG application from Level 4 through the whole lifecycle of this level.
Version every prompt in a registry with a production label, and record experiments with their parameters, metrics, and artifacts.
Gate every change in CI with the evaluation suite, and show the gate blocking a deliberately regressed prompt.
Run the application behind input, output, and agent guardrails, with every block logged.
Serve it as a streaming FastAPI backend and a Streamlit frontend, packaged with Docker Compose.
Build and push commit-tagged images through GitHub Actions, and deploy them to EC2 with CodeDeploy behind a load balancer with Auto Scaling and Secrets Manager.
Monitor it with Grafana dashboards and at least one working alert, and trace requests with cost and latency per step.
Demonstrate one rollback, of either a prompt or an image, and write the runbook for one incident type.
Final result: a deployed LLM application where every change is versioned and evaluated before release, and whose health, quality, and cost you can see while it runs.

Level 10 completion outcome

By the end of this level, you should be able to:

Explain what makes an LLM application harder to operate than conventional software, and what a release consists of.
Structure an application so that prompts, models, retrieval settings, and tools are configuration rather than code.
Track experiments and version prompts, promoting and rolling back without a code deployment.
Gate every change, including prompt and model changes, on an automated evaluation suite.
Run guardrails on inputs, outputs, and agent actions, and measure what they cost and what they wrongly block.
Serve an application as a streaming FastAPI backend with a thin frontend, packaged in containers.
Build a CI/CD pipeline that tests, evaluates, builds, and tags images before anything is deployed.
Deploy on AWS with automated, health-checked releases, load balancing, and scaling sized to provider limits.
Monitor infrastructure, application metrics, cost, and answer quality, and alert on what needs a human.
Respond to LLM-specific incidents with fallbacks, rollbacks, and runbooks.
